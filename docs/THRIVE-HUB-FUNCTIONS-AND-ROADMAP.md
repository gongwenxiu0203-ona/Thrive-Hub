## 2. 角色、功能权限和数据范围

### 2.1 角色名称

| 数据库角色 | 页面统一名称 | 说明 |
|---|---|---|
| `ADMIN` | 管理员 | 系统管理和业务管理 |
| `USER` | 内部员工 | 不再使用“普通员工”的页面称呼 |
| `BRAND` | 品牌方 | 只访问被授权的品牌/客户数据 |
| `CHANNEL` | 渠道商 | 只访问对应渠道及确认流程 |

### 2.2 统一权限结构

系统使用细粒度 leaf 权限，权限等级为：

```text
NONE < READ < EDIT < MANAGE
```

- `READ`：查看页面和记录。
- `EDIT`：包含 READ，并可创建、编辑、提交。
- `MANAGE`：包含 EDIT，并可执行删除、恢复、作废、管理级确认等动作。
- 页面入口、按钮显示、API/Server Action、数据范围应同时遵守对应 leaf。

### 2.3 财务与经营的当前数据口径

- 管理员和内部员工：具备对应 leaf 后，在财务与经营板块查看全量业务数据。
- 管理员和内部员工：创建财务记录时，客户、合同下拉可选择系统内全部有效记录。
- 品牌方、渠道商：继续按品牌、客户、渠道关系隔离，规则没有被放开。
- 财务中的全量客户/合同“引用能力”不等于获得客户管理或合同管理的编辑权限。
- 已删除客户、已删除合同、状态不符合当前流程的合同仍不可选。

### 2.4 仍存在的权限收敛问题

middleware 和 Sidebar 已主要改为 leaf 判断，但部分页面、API 和 Server Action 仍叠加角色硬判断或没有完整使用 leaf。详细问题见第 15 节。

## 4. 登录、注册和账号安全

### 操作路径

- 登录：`/login`
- 邀请/注册：`/register`
- 待审核账号：`/pending`
- 忘记密码：`/forgot-password`
- 重置密码：`/reset-password`
- 个人资料及密码设置：`/settings`

### 已实现

- JWT + httpOnly Cookie 登录。
- 注册审核、账号状态控制。
- 找回密码 token 和重置页面。
- 密码修改成功后的业务流程基础。

### 当前缺口

- 密码重置目前仍走通用 SMTP 发送器；生产未配置 SMTP 时只会把内容记录到服务器日志，不会真正发信。
- 腾讯云 SES 模板和 API 尚未接入，因此“找回密码”和“密码修改成功通知”没有形成生产邮件闭环。
- 邮件投递失败、退信、重试和发送审计尚未实现。

```text
  → 合同详情 /contracts/[contractId]

  → 模板库 /contracts/templates
```

### 已实现

- 标准新建、上传已有 Word/PDF、交易型合同上传。

- 盖章、签署、版本管理、完成归档。

### 已知权限缺口

1. `/contracts` 和 `/contracts/reviews` 的页面入口没有完整使用对应 leaf，NONE 用户存在直达风险。
2. 审核动作仍主要使用 `contracts.records` 加 ADMIN 角色判断，没有完全切换到 `contracts.reviews`。
3. 完成/签署动作没有完整使用 `contracts.signing`。

5. 模板 READ/EDIT/MANAGE 的实际能力与页面说明不完全一致。
6. `contractScope()` 当前对管理员和内部员工直接返回全量，因此合同列表的“我的/全部”切换实际不起作用；页面文案却仍说明默认只看相关合同。
7. 内部员工可以查看、编辑全量合同，但新建合同的客户下拉仍按 customer mine 过滤，形成“已有合同全量、新建只能选本人客户”的不一致口径。

## 9. 推广数据 BI

### 操作路径

```text
推广数据 BI /bi
  → 销售看板
  → 明细数据
  → 数据上传
  → 数据清理
  → ASIN 匹配
```

### 已实现

- 日期、品牌、客户、平台、项目、站点、联盟商、ASIN 等多维筛选。
- 销售额、佣金、销售数量、图表和分页明细。
- 按当前筛选导出。
- Excel/CSV 上传、字段映射、批次管理。
- 明细批量关联客户、软删除、撤销、操作日志。
- 清理预览、二次确认、ASIN 匹配。
- 活动批次与软删除批次已统一过滤；客户对账拉取与 BI 看板使用同一活动数据和自然日口径。

### 大文件真实限制

- 当前已有临时文件和样本解析优化，但还不是流式解析、分片上传或后台导入。
- 浏览器解析请求约 90 秒超时，Next/Nginx 请求上限约 110MB。
- XLSX 内部 XML 可能膨胀约 10 倍；历史 82MB 文件曾解压到约 748MB，并触发 2GB 服务器 OOM。
- 完整导入仍可能在单个长事务中造成内存、超时和 SQLite 锁问题。

### 建议的正式方案

```text
浏览器分片上传
→ 服务器落临时文件/COS
→ 后台 Worker 流式解析
→ 每 500~2000 行分批写入
→ 保存任务进度和失败行
→ 前端轮询/推送进度
→ 可暂停、重试和断点续传
```

### 权限缺口

- BI 页面页签和按钮仍使用 `isStaff` 角色判断，没有完全按 `bi.view/import/export/manage` 显隐。
- 部分 ASIN 上传/模板 API 只检查登录。
- 上传页可见批次范围与删除批次的范围不一致。

## 11. 结算中心

### 11.1 客户对账

```text
结算中心 /finance
  → 客户对账
  → 客户聚合详情 /finance/customers/[customerId]
  → 固费 / 销售佣金
  → 拉取 BI（销售佣金）
  → 提交客户确认 或 跳过客户确认
  → 确认/纠正销售额
  → 生成对账报告 PDF
  → 开具 Invoice
```

已实现规则：

- 固费和销售佣金分别建账，新记录禁止 `BOTH`。
- 同客户、同费用流、周期重叠时禁止重复创建。
- 销售佣金从 BI 拉取实际销售额并计算佣金。
- 提交客户确认：选择确认人，进入待确认。
- 跳过客户确认：选择无异议或有异议；唯一可纠正字段是销售额。
- 固费不接受销售额异议。
- 对账 PDF 可包含佣金 BI 汇总、差额提示和明细。
- 确认后不会自动创建 Invoice 草稿；流程提示用户开具 Invoice。
- 软删除、7 天恢复和过期清理。
- 三个自然日未正式开具 Invoice 时创建站内提醒。

明确问题：

1. 新客户聚合详情与旧 `/finance/reconciliations/[id]` 提交接口并存；旧文案仍提到已经取消的“订单数量异议”。
2. 三日提醒依赖用户进入系统时扫描，不是真正的后台定时任务。
3. 旧 Settlement 手工状态与 Invoice/AR 自动回传可能产生两个数据真相。
4. 客户对账邮件尚未接入。

### 11.2 渠道分账

```text
结算中心 /finance
```

- 凭证支持图片/PDF，限制 20MB。
- 付款完成后周期锁定。

待处理：

- 相似分账可在确认后重复创建，重复结算口径需要业务决策。
- 旧 `push`、`generate-periods` 与新逐周期 `review-flow` 并存。
- 渠道确认和结果邮件尚未接入。

### 11.3 联盟商结算

- 列表查看需要 `finance.affiliate_reconciliation=READ`。
- 编辑和上传凭证需要 `EDIT`。

### Reply-To 管理方案

腾讯云 `SendEmail` API 的 `ReplyToAddresses` 是每次发送时传入的回复地址，因此无需在模板中写死。推荐在 Thrive Hub 管理员面板增加“邮件设置”，由具备 `admin.api_access=MANAGE` 的管理员修改：

- 全局默认 Reply-To。
- 密码与账号安全 Reply-To。
- 客户对账 Reply-To。
- 渠道分账 Reply-To。
- Invoice 与财务 Reply-To。
- 联盟资源/项目邮件 Reply-To。

业务专用地址未填写时回退到全局默认地址。保存时需要验证邮箱格式、记录修改人和修改时间，并在发送日志中保存当次使用的 Reply-To 快照。SecretId/SecretKey 仍只保存在服务器环境变量中，不允许通过管理员页面读取或修改。

当前项目没有通用系统设置表；真正实现管理员页面持久化配置时，可能需要新增设置表或使用独立安全配置服务。这属于后续 Schema 设计，实施前必须按数据库结构变更流程单独说明并取得确认。本轮只记录方案，不修改 Schema。

### 应用接入顺序

1. 在生产 `.env` 配置 SecretId、SecretKey、地域、发信地址和模板 ID；绝不提交密钥。
2. 新增统一邮件服务适配层，支持腾讯云 SES API、模板参数校验和超时。
3. 先接密码重置和密码修改通知，完成最小闭环。
4. 接客户对账待确认/结果邮件。
5. 接渠道分账待确认/结果邮件。
6. 接 Invoice 邮件和 PDF 附件。
7. 把三日提醒迁移到独立定时任务，并增加邮件。
8. 增加发送日志、幂等键、重试、投递/退信回调和告警。

## 15. 已确认 Bug 与高风险技术债

### P0：应优先处理

1. **项目 Action 行级鉴权缺口**：部分操作只验证 leaf，不验证目标项目是否在当前用户数据范围内。
2. **合同/任务/联盟详情等页面 leaf 直达缺口**：配置 NONE 后仍可能直接打开部分页面或 API。
3. **BI ASIN API 权限缺口**：部分上传/模板接口只检查登录。
4. **密码重置没有生产邮件闭环**：SMTP 未配置时可能仅写服务器日志。
5. **业务文件没有异地备份**：当前日备份只覆盖 SQLite，不覆盖上传附件、合同模板、生成件、付款回单等文件。
