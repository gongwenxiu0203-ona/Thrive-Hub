# 格式合同与项目确认书改造方案

更新：2026-08-31。状态：用户已确认Schema新增，第一阶段数据结构与纯规则基础已实现；尚未接入在线业务入口或应用本地/生产数据库。

## 1. 已确认的业务边界

- 同一客户下，先按主格式合同分类，再按项目确认书切换。
- 每份已生效确认书独立计费、独立生成对账；多份可同时生效，日期重叠不互相覆盖。
- 主格式合同存通用条款与主体信息，不再为新模式额外生成一套重复费用。
- 各确认书仅为实际选定的收费项目生成对账，不因为存在确认书就强制产生固费和佣金两类费用。
- 合并申请开票不合并底层计费归属：每一申请明细保留客户、主合同、确认书、对账记录来源。
- 旧合同继续使用旧算法和历史记录；不自动转换、不重算已确认金额、不批量补出重复对账。

| 确认书 | 月费金额币种、佣金比例、结算周期、付款条件 | 形成独立收费规则；未填必要参数不允许生效 |

| 确认书 | 存量/增量确认方式及双方确认清单 | Campaign、Publisher、月度门槛、全量四种口径；保存清单/说明/证据 |

## 3. 计费规则与现有系统差异

### 3.1 两个维度不能混为一个佣金类型

收费模式（GMV服务佣金 / 总包佣金）与计佣范围（Campaign / Publisher / 超门槛 / 全量）分开配置。月费等其他费用是独立收费项。

- GMV服务佣金：可计佣有效GMV × 约定比例。
- 月度门槛：max(当月有效GMV − 当月门槛, 0) × 比例。
- 现有 `src/lib/commissionCalc.ts` 的 THRESHOLD 是达标后全额计佣，不能直接作为新模板的超门槛规则；旧合同算法保持原样。
- Campaign/Publisher并非简单“创建时间之后的才计佣”：模板也包含重新激活、维护、优化、实际推动合作等情形，需确认清单与人工归类入口。
- 无有效订单/归因明细时，不允许假装仅凭汇总GMV就能完成Campaign或Publisher分流；应提示补数据或提交人工核定及证据。
- 同一订单多种归因命中需去重。用户确认同一订单只归属一份确认书；多份命中时提示冲突并要求确定唯一归属，未解决不得重复计佣。唯一订单标识需包含平台/店铺等命名空间，不能仅用裸订单号。
- 总包佣金：合同/确认书仅填写总包佣金值，不要求在合同阶段拆分渠道成本。销售佣金对账显著提醒核对并修改本期实际抽佣比例，保存操作人及前后值；不擅自推算总包与渠道分成。总包值与本期实际抽佣比例分开存储，不能静默将前者当作后者。
- 固定项目费/其他：模板没有完整金额与分期结构；需补充系统字段并人工确认，不能默认为月费。
- 新规则比例输入统一明确百分数语义，覆盖1%、0.5%等边界；不继续依靠“大于1才除100”推断。

### 3.2 终止与尾期

模板约定终止后的30日尾期佣金，受终止前已形成的归因记录及违约例外等条件限制，确认书可另约定。因此新模式需区分：服务结束、常规费用截止、尾期佣金截止。

- 终止确认书仅影响其自身，不影响同主合同其他确认书。
- 终止主合同应预览列出受影响确认书及对账记录，再确认处理。
- 未开始的常规费用按终止规则作废；尾期佣金单独标识，不延长普通月费周期。
- 已确认/已开票/已核销历史不直接改写；差额调整单留痕。
- 客户结束合作的单合同联动、多合同不自动联动规则继续保留，联动时必须展示确认书影响范围。

### 3.3 规则快照

现有 `src/lib/reconciliationCalc.ts` 重算时仍读取当前 Contract 的部分佣金字段。新模式按确认书的生效规则版本计算，并保存对账规则快照；修改确认书不静默改变已出对账。

## 4. 页面与操作

```text
客户对账 / 客户A
  主格式合同：[合同A] [合同B]
  项目确认书：[确认书01 · 生效] [确认书02 · 生效] [确认书03 · 已终止]
  当前确认书：周期 / 平台站点 / 费用规则 / 币种 / 状态
  +----------------------------+----------------------------+
  | 固费对账                   | 销售佣金对账               |
  | > 历史周期（折叠）         | > 历史周期（折叠）         |
  | 当前周期                   | 当前周期                   |
  | > 未开始周期（折叠）       | > 未开始周期（折叠）       |
  +----------------------------+----------------------------+
  已选明细（显示合同与确认书来源）         [合并提交开票申请]

主格式合同详情
  主体 / 联系人 / 收款账户 / 格式合同文件
  项目确认书列表                          [+新增] [上传确认书]
  编号   项目/品牌   周期   收费模式   状态   操作
  01     项目甲      ...    GMV佣金    生效   查看/追加版本/终止
  02     项目乙      ...    月费+佣金  生效   查看/追加版本/终止
```

流程：建立主合同 → 新建/上传确认书 → 核对范围与收费规则 → 签署生效 → 幂等生成该确认书的对账计划 → 对账 → 开票申请 → 财务开具 → 文件和收款状态回传原记录。

草稿/未生效确认书不生成正式账单；反复执行生成不能重复创建。同周期不同确认书必须各自保留。

## 5. 已获授权的数据库设计方向

- 新增项目确认书、确认书版本及收费规则记录，关联现有Contract。
- 范围/商品/存量确认清单按结构化明细保存，并保留来源证据。
- CustomerReconciliation新增可空确认书及规则版本关联；现有contractId仍表示主合同。
- 自动生成key包含确认书、收费项、周期；不能继续仅以主合同和日期判断重复。
- 审查发现当前自动键为 `contract:${contractId}:${type}:${index}`（`src/lib/customerReconciliationPlan.ts`）；手工重叠检查在 `src/app/api/finance/reconciliations/route.ts` 按合同进行。两者都必须增加确认书维度，连同补齐、恢复和终止逻辑一起修改。
- 开票明细保留确认书追溯关联/快照；现有InvoiceContract及InvoiceReconciliation关联不删。
- 财务流程手工开票申请（不来源于对账）也必须能明确选择确认书；仅沿对账关系追溯不足以覆盖这一入口。
- 对旧记录使用空确认书关联明确识别旧模式，不伪造历史确认书。
- 不删除旧业务字段，不改旧编号，不清空记录。用户已在结构变更提醒后回复确认；新迁移仅在隔离空库测试，尚未应用业务数据库。

## 6. 实施顺序和验收

1. 总包在对账阶段核定实际抽佣比例、订单唯一归属已确认；批准准确的Schema方案后实施。
2. 新增数据结构、独立规则计算及测试，旧路径保留。
3. 主合同/确认书创建上传、人工核对、生效版本及终止。
4. 对账按合同→确认书切换、幂等生成、尾期和调整。
5. 开票申请及Invoice预填和下载回传接入来源信息。
6. 测试旧合同兼容、双确认书同周期、只选一份、重新生成、1%费率、门槛临界值、退款去重、终止尾期、历史不可覆盖、权限、币种和合并开票。

第一阶段新增6表和旧表可空来源字段，新增纯计费、周期、确认书输入校验与回归测试。未接API/UI，未生成真实对账、未修改本地或生产数据库，未commit/push/deploy。

### 第一阶段验证与接入限制

- `npx.cmd tsx scripts/contract-confirmation-rules-test.ts`：新算法、百分比、总包人工比例、币种、周期和独立键通过。
- `npx.cmd tsx scripts/contract-confirmation-draft-test.ts`：多账户、多国家行、自定义选项、草稿/生效条件、币种和快照通过。
- `node scripts/contract-confirmation-schema-test.cjs`：只在临时生成的合成SQLite库执行；验证旧记录字段保留、唯一归属、多账户/范围、外键完整性以及迁移后的Schema零差异。需要支持node:sqlite的Node版本，本地Node24验证通过。
- Prisma validate、全量TypeScript检查通过；未运行会自动迁移业务库的npm run build。
- 下阶段必须先完成模式隔离、权限入口、账户/客户归属校验、确认书规则快照与不可覆盖版本，才能开放生效操作；不能仅有Schema便将主合同标记FRAMEWORK。
- 固定项目费、其他费用、尾期、确认书追加版本和订单归属审核尚未接入工作流；纯周期函数仅实现已明确的30日固费/自然月佣金，不擅自生成这些其他账项。

## 7. 2026-08-31 补充确认：账户与下拉交互

- 乙方收款账户支持一至多个，从财务资料选择并保存合同签署快照；开票时选择实际收款账户，不因多账户重复计费。
- 推广范围按国家（站点）一行，可新增/删除多行；每行独立保存国家、销售平台、使用Program、第三方平台的关联，不在不同行之间做笛卡尔积。
- 以上字段标准值用可搜索下拉；“其他”进入手动新增，允许维护多个自定义值；不覆盖已有标准项。自定义值写入前去空白和查重，保留来源。
- 合同所有具备既有选项或明确枚举的字段均采用下拉；客户、人员、账户等业务对象使用真实系统数据关联，金额、日期、地址和备注仍使用对应输入控件。
- 需要多选的字段支持多选；国家为行维度，多个国家通过新增行实现，不将多个国家压成一段文本。
- 下拉依赖数据未加载或无权限时明确提示，不把失败伪装为空选项。
